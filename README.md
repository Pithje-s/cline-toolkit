# cline-toolkit

Готовый набор конфигурации для Cline: правила поведения агента, навыки, воркфлоу-команды
и шаблон MCP. Собрали один раз — используете во всех проектах и делитесь с командой.

**v0.5.1** · [История изменений](CHANGELOG.md) · [Каталог компонентов](CATALOG.md) ·
[Измерения](EVAL.md) · [Как внести вклад](CONTRIBUTING.md) · MIT

## Быстрый старт

```powershell
git clone https://github.com/Pithje-s/cline-toolkit.git
cd cline-toolkit
powershell.exe -ExecutionPolicy Bypass -File .\install.ps1 -DryRun   # план без записи
powershell.exe -ExecutionPolicy Bypass -File .\install.ps1            # установить
```

Перезапустите Cline, чтобы он подхватил правила, навыки и MCP-серверы.

| Действие | Команда |
|---|---|
| Откатить установку | `.\uninstall.ps1` (строго по манифесту, посторонние файлы не трогает) |
| Вернуть MCP-конфиг из бэкапа | `.\uninstall.ps1 -RestoreMcpBackup` |
| Проверить набор | `.\tests\run-tests.ps1` |
| Проверить валидность задач eval | `.\eval\run-eval.ps1 -ValidateTasks` |
| Измерить стоимость контекста | `.\eval\measure-context.ps1` |

Ключ Tavily в шаблоне — плейсхолдер `YOUR_TAVILY_API_KEY`, его нужно заменить своим
(см. [MCP-серверы и безопасность](#mcp-серверы-и-безопасность)).

## Что внутри

| Слой | Файлов | Когда грузится в контекст | Что даёт |
|---|---|---|---|
| `rules/` | 3 | **всегда** | дисциплина: данные vs команды, план, запрет заглушек, git, безопасность, язык ответа |
| `skills/` | 10 | по требованию (метаданные — всегда) | ревью, разбор стектрейса, research, починка, архитектура, PowerShell |
| `workflows/` | 21 | по вызову `/команды` | `/plan`, `/review`, `/verify`, `/repair`, `/precommit-check`, система memory-bank |
| `mcp/` | 1 шаблон | — | `tavily` включён, остальные серверы — выключенные заготовки |

Подробно по каждому файлу — [CATALOG.md](CATALOG.md). Что именно меняется в работе
агента — ниже.

### Навыки

| Навык | Когда срабатывает |
|---|---|
| `verify-changes` | перед завершением любой задачи, менявшей файлы: доказать diff'ом и прогоном |
| `independent-review` | «ревью», «проверь дифф» — вердикт BLOCKER/MAJOR/MINOR без переписывания кода |
| `error-stack-analyzer` | падения и стектрейсы: первая строка в вашем коде и root cause |
| `repair-loop` | упали тесты/сборка/линт: исправить → перепроверить → повторить |
| `external-research` | локальные знания исчерпаны: точные запросы или готовые ссылки |
| `design-twice` | крупная фича: два существенно разных подхода и сравнение до кода |
| `safe-dependency` | установка пакета: анти-typosquatting, стабильная версия |
| `system-optimizer` | «ускори систему»: правки кодом с бэкапом, а не советами |
| `powershell-safety` | генерация PowerShell-команд и `.ps1`, зависший терминал, нужны права администратора |
| `next-step-orchestrator` | задача завершена: 1–2 готовых промпта для следующего шага |

### Что это меняет на практике

- Агент не пишет «готово», пока не показал доказательство: `git diff`, код выхода,
  хвост вывода (`verify-changes`).
- Не оставляет заглушек и «... existing code ...» — это автоматический BLOCKER
  (`Zero Placeholders` + `independent-review`).
- Ревью идёт отдельным проходом «глазами другого инженера», а не переписыванием кода.
- Неясное ТЗ — вопрос до работы; три неудачи подряд — эскалация в `external-research`,
  а не слепой перебор.
- Настройка ОС/софта делается скриптом (при необходимости с самоподъёмом UAC),
  а не списком «зайдите в настройки и нажмите кнопку».

## Установка

### Куда кладутся файлы

| Слой | Глобально (все проекты) | В проекте |
|---|---|---|
| Правила | `Documents\Cline\Rules` | `.clinerules/` или `.cline/rules/` |
| Воркфлоу | `Documents\Cline\Workflows` | `.clinerules/workflows/` |
| Навыки | `~/.cline/skills/` | `.cline/skills/` (рекомендуется), `.clinerules/skills/` |
| MCP | `~/.cline/data/settings/cline_mcp_settings.json` | настройки workspace |

> Cline читает глобальные правила и воркфлоу только из `Documents\Cline\Rules` и
> `Documents\Cline\Workflows`. Плоские `.md` в `~/.cline` и `~/.cline/workflows`
> современные версии не читают (проверено по коду расширения Cline 4.1.x).
> На Windows `~` = `C:\Users\<USER>`, `Documents` — «Мои документы» (может быть
> перенаправлена в OneDrive, Cline берёт её через `MyDocuments`).
> Глобальный навык с тем же именем, что и проектный, имеет приоритет.

Для команды удобнее проектный вариант: скопируйте `rules/`, `workflows/`, `skills/`
в `.cline/` и `.clinerules/` внутри репозитория — тогда конфигурация версионируется
вместе с кодом и её видят все.

### `install.ps1`

1. Копирует правила, воркфлоу и навыки в канонические каталоги выше.
2. **Сливает** шаблон MCP с вашим конфигом: серверы, ключи, `autoApprove` и
   `disabled` сохраняются, из шаблона добавляются только отсутствующие. Перед
   записью — бэкап `cline_mcp_settings.json.bak-<timestamp>`, после записи —
   посерверная сверка; при расхождении файл восстанавливается из бэкапа и
   установка останавливается.
3. Пишет манифест `~/.cline/.cline-toolkit-manifest.json` (путь + SHA256 каждого файла).
4. Удаляет файлы прошлой установки, которых больше нет в репозитории, — только при
   совпадении хеша. Изменённые вручную остаются и перечисляются в отчёте.

Параметры: `-DryRun` (план без записи), `-NoPrune` (не удалять устаревшее),
`-ForceMcpTemplate` (заменить невалидный MCP-конфиг шаблоном), `-ClineDir`,
`-DocumentsDir`, `-RulesDir`, `-WorkflowsDir`, `-SkillsDir`, `-McpFile`,
`-ManifestFile`, `-KeepLegacyCopies`.

### `uninstall.ps1`

Удаляет только то, что записано в манифесте: `-DryRun` (план), `-Force` (удалить
даже изменённые вручную), `-RestoreMcpBackup` (вернуть MCP-конфиг из самого свежего
бэкапа; текущий перед этим сохраняется в `.pre-restore-<timestamp>`). Посторонние
файлы и сам `cline_mcp_settings.json` не трогаются.

## Измерения (eval)

Набор — это гипотеза, поэтому он измеряется, а не принимается на веру. Три вещи
считаются машинно:

1. **Стоимость контекста.** Правила и метаданные навыков уходят в каждый диалог.
   Замер v0.5.0: **8 304 символа** always-on (~2 076–3 775 токенов) — после выноса
   PowerShell-деталей в навык было 18 894.
2. **Качество результата.** 5 задач-фикстур со сломанным состоянием и объективной
   проверкой: заглушки, шумные комментарии, изменения вне scope, «готово» без
   доказательств. Отдельная задача проверяет качество тестов мутациями.
3. **Валидность самих задач.** Проверка «сломанная фикстура падает, эталонное
   решение проходит» гоняется в CI — задачи не должны «сгнить».

Методика, метрики и границы применимости — [EVAL.md](EVAL.md). Полный A/B «с набором правил
против без» требует внешнего headless-агента: раннер принимает команду агента
параметром и не выбирает её за вас.

## MCP-серверы и безопасность

`mcp/cline_mcp_settings.json` — шаблон с одним включённым сервером и заготовками:

| Сервер | Назначение | Статус |
|---|---|---|
| `tavily` | веб-поиск и research с AI-результатами (нужен API-ключ) | включён |
| `fetch` | загрузка и парсинг веб-страниц | `disabled: true` |
| `filesystem` | ограниченный доступ к файловой системе | `disabled: true` |
| `git` | операции с локальным репозиторием | `disabled: true` |
| `memory` | долговременная память между сессиями | `disabled: true` |

Чтобы включить сервер — поставьте `"disabled": false` и укажите реальные пути
(для `filesystem` и `git`). JSON не поддерживает комментарии, поэтому описания
живут в этой таблице.

**Аудит обязателен.** MCP-сервер — это код с реальными правами. Перед подключением
пройдите чек-лист [mcp/SECURITY.md](mcp/SECURITY.md): источник, известность,
запрашиваемые права, чувствительные пути, способ передачи секретов, версия.
Правила требуют явного подтверждения пользователя на каждый новый сервер.

**Ключ Tavily.** В репозитории только плейсхолдер `YOUR_TAVILY_API_KEY`. Реальный
ключ хранится в вашем локальном `cline_mcp_settings.json` (вне репозитория):
получите его на https://tavily.com (раздел API Keys) и замените плейсхолдер —
либо дайте `install.ps1` перенести существующий ключ автоматически. Если ключ
попал в публичный репозиторий — отозовите и перевыпустите.

## Команды и рецепты

Навыки вызываются обычной фразой, воркфлоу — слэш-командой или тоже фразой.

| Хочу | Что написать |
|---|---|
| Ревью перед коммитом | `Use independent-review on this diff.` или `/review` |
| Доказать, что правка работает | `Run verify-changes before committing.` или `/verify` |
| Разобрать падение | `Use error-stack-analyzer on this stack trace: <вставка>.` |
| Починить по стектрейсу | `Use repair on this: <стектрейс>.` или `/repair` |
| Спланировать крупную фичу | `Use design-twice for <фича>, потом согласуем.` |
| План задачи | `/plan` |
| Финальный чек-лист | `Run precommit-check.` или `/precommit-check` |
| Найти решение во внешних источниках | `Use external-research to find <тема>.` |
| Восстановить состояние проекта в новой сессии | `/memory-bank`, затем `продолжаем задачу про <фича>` |
| Сжать раздутый memory-bank | `/memory-consolidation` |

> В начале новой сессии сначала подгружайте `memory-bank`-контекст: агент получает
> состояние проекта и не переспрашивает то, что уже решено.

## Кастомизация

Набор «opinionated», но правится по месту. Чаще всего меняют:

| Что | Где | Как |
|---|---|---|
| Язык ответов, запрет иероглифов | `rules/02-quality-git.md` → «Язык ответа» | ослабить/убрать пункт под свой проект |
| Лимит попыток (3) | `rules/03-workflow-search.md` + skill `repair-loop` | заменить число в обоих местах |
| Порог обязательного плана (>1 файл / >20 строк) | `rules/01-core.md` → «Обязательный план» | поднять под размер своих задач |
| Git-дисциплина, Conventional Commits | `rules/02-quality-git.md` → «Git» | заменить на правила команды |
| Набор MCP-серверов | `mcp/cline_mcp_settings.json` | `disabled: false` + реальные пути |
| Набор навыков и воркфлоу | `skills/`, `workflows/` | удалить ненужное: лишнее не вредит, но занимает место в `/`-меню |

Параметры по умолчанию собраны в [`config.example.json`](config.example.json) —
скопируйте в `config.json` и используйте как чек-лист:

```json
{ "language": "ru", "repairAttempts": 3, "plan": { "maxFiles": 1, "maxLines": 20 },
  "cjkRuleEnabled": true, "mcp": { "allowlist": ["tavily"] } }
```

> Конфиг **advisory**: правила — это Markdown, поэтому скрипты проверяют и подсказывают
> значения, но не переписывают прозу. `validate.ps1` валидирует JSON; соглашения для
> команд можно задавать env-переменными (`CLINE_LANG`, `CLINE_REPAIR_ATTEMPTS`,
> см. блок `env` в конфиге).

## Автоустановка через ИИ-агента

Если не хочется раскладывать руками — отдайте агенту промпт ниже: он сам скачает
репозиторий и запустит установщик.

<details>
<summary>Промпт для агента (развернуть)</summary>

```text
Ты устанавливаешь cline-toolkit — набор конфигурации Cline (правила, навыки,
воркфлоу, MCP-настройки) — на текущей машине.

Репозиторий: https://github.com/Pithje-s/cline-toolkit (ветка main).
Если пользователь указал другую ветку или форк — используй её.

Шаг 1. Скачай репозиторий во временную папку и запомни путь как $repo.
- git: git clone --depth 1 https://github.com/Pithje-s/cline-toolkit.git "$env:TEMP\cline-toolkit"
- без git: скачай zip ветки main, распакуй Expand-Archive в "$env:TEMP\cline-toolkit".

Шаг 2. Запусти установщик (он сам раскладывает файлы по каноническим каталогам Cline):
  powershell.exe -ExecutionPolicy Bypass -File "$repo\install.ps1"
Сначала можно показать план: тот же вызов с -DryRun.
Вручную копировать не нужно: install.ps1 сливает MCP-конфиг с существующим (ключи и
серверы сохраняются), делает бэкап и пишет манифест установки.

Шаг 3. Проверь результат.
- Выведи из вывода установщика: сколько файлов правил/воркфлоу/навыков установлено,
  сколько MCP-серверов сохранено и сколько добавлено.
- Убедись, что cline_mcp_settings.json — валидный JSON без BOM.
- Ключ Tavily: если остался плейсхолдер YOUR_TAVILY_API_KEY — скажи пользователю,
  что его нужно заменить; реальный ключ не вставляй и никуда не публикуй.
- Удали временную папку $repo.

Шаг 4. Отчитайся коротко: что установлено, что сохранено из прежнего конфига,
нужен ли ручной ввод ключа Tavily.

Используй PowerShell. Не используй Format-Table для вывода (он вешает терминал),
не запускай интерактивных команд.
```

</details>
