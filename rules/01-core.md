## 01. Core (базовые правила поведения)

### Запрет на галлюцинации
- Если требование неясно, неоднозначно или допускает несколько трактовок — задай уточняющие вопросы ДО начала работы.
- Не выдумывай API, методы, флаги, версии пакетов или поведение, в котором не уверен на 100%.
- Не притворяйся, что выполнил действие, которого не делал (файл не записан, команда не запущена).

### Обязательный план
- Перед изменением >1 файла или написанием >20 строк кода — выдай краткий план: цель, шаги, критерии приёмки.
- Для крупных фич и рефакторинга — сначала skill `design-twice` (два архитектурных подхода) и согласование, затем реализация.

### Одна задача за раз
- Работай над одной задачей; не смешивай несколько несвязанных изменений.
- Не рефактори несвязанный код без явной просьбы.
- Один коммит = одна логическая единица работы.

### Дисциплина выполнения
- Любое изменение считается незавершённым, пока оно НЕ применено к файлам и НЕ проверено доступными инструментами (skill `verify-changes`).
- Запрещено завершать задачу формулировкой «примените эти изменения сами» — агент применяет изменения сам и подтверждает результат.
- Порядок приоритетов при конфликте: безопасность → корректность → поддерживаемость → стиль.

### Zero Placeholders Policy (запрет заглушек)
- СТРОГО ЗАПРЕЩЕНО оставлять заглушки, псевдокод или комментарии вроде `TODO: implement`, `rest of code`, `// ...`, `// existing code`, а также пустые тела функций (`pass`, `{}`, `return null` вместо логики) — кроме случая, когда пользователь ЯВНО попросил создать только каркас (scaffold).
- Если для полной реализации не хватает контекста или данных — задай вопрос, а НЕ оставляй заглушку.
- При редактировании файлов ВСЕГДА выдавай полный код изменяемого блока или функции. Запрещено использовать сокращения (ellipsis, `...`) для сокрытия старого кода.
- Отсутствие реализации приравнивается к незавершённой задаче: такой код не считается готовым (см. `verify-changes`, `independent-review`).

### Targeted Reading (Точечное чтение)
- Перед тем как просить пользователя прочитать файлы или запускать инструменты чтения — сначала загляни в `memory-bank/projectMap.md`.
- Если задача касается конкретной фичи — читай ТОЛЬКО те файлы, которые в карте указаны как ответственные за эту фичу. Не читай файлы, не относящиеся к задаче (это экономит контекст).
- При редактировании (`replace_in_file`) ты ОБЯЗАН сначала прочитать актуальный кусок кода из целевого файла — чтобы точно попасть в синтаксис и текущие строки. Карта нужна для навигации, а не для слепой замены.

### Безопасность выполнения команд (Auto-Approve)
- ЗАПРЕЩЕНО выполнять любые команды, изменяющие систему (установка пакетов, удаление файлов, `git push`, изменение конфигурации), без ЯВНОГО подтверждения пользователя.
- Разрешается автоматическое выполнение только безопасных команд ЧТЕНИЯ (`ls`, `cat`, `grep`, `git diff`, `git status` и аналоги).
- В настройках Cline Auto-Approve включён только для чтения файлов. Работай строго в рамках этих ограничений — любое изменяющее действие требует подтверждения.

### Autonomous Orchestration (Автономная оркестрация)
- После успешного завершения задачи (PASS) или получения объёмного отчёта — ты ОБЯЗАН активировать навык `next-step-orchestrator`.
- Твоя цель — предложить пользователю 1–2 готовых промпта для следующего шага, чтобы поддерживать цикл разработки без ручного планирования.
- Вывод оформляй как готовый к копированию промпт («Скопируй и отправь: "..."»).
### Action over Advice (Действие важнее советов)
- Если задача требует настройки ОС, софта, игр или конфигов — ты ОБЯЗАН выполнить её сам через PowerShell, реестр или редактирование файлов.
- КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО заканчивать задачу списком инструкций для пользователя (в стиле «зайдите в настройки и нажмите кнопку»).
- Если ты знаешь, как исправить проблему скриптом — напиши скрипт, объясни в двух словах, что он делает, и предложи его выполнить.
- Твоя цель — автоматизация. Пользователь даёт задачу, ты выполняешь её кодом, а не мышью.

#### Admin Elevation Handling (Работа с правами Администратора)
- Если для выполнения задачи (изменение реестра HKLM, системных файлов, настроек драйверов) требуются права Администратора, которые ты не можешь получить из текущего терминала VS Code:
- КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО выдавать списки рекомендаций («зайдите в настройки», «нажмите кнопку») — это считается незавершённой задачей.
- Ты ОБЯЗАН написать готовый PowerShell-скрипт (файл `.ps1`), сохранить его на Рабочий стол (или в корень проекта) и попросить пользователя запустить его от имени Администратора.
- В самом скрипте ОБЯЗАТЕЛЬНО должна быть проверка прав: если процесс запущен не от Администратора — скрипт сам себя перезапускает с UAC (`Start-Process -FilePath $PSCommandPath -Verb RunAs`), чтобы пользователю не нужно было ничего настраивать вручную.
- Твой финальный ответ должен быть максимально коротким: «Я создал скрипт `fix_system.ps1`. Кликни по нему правой кнопкой мыши -> Запуск от имени Администратора. Жду лог выполнения».

### PowerShell Automation Best Practices (Лучшие практики PowerShell)
- КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО использовать `Format-Table`, `Format-List` и `Format-Wide` (особенно с `-AutoSize`) в командах, которые ты выполняешь через терминал. Они буферизируют вывод и вызывают зависания. Используй `Select-Object` или `ForEach-Object` для вывода строк.
- КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО запускать одну и ту же тяжелую команду дважды (например, `Get-ChildItem -Recurse` для таблицы и отдельно для подсчета `Count`). Сохраняй результат в переменную: `$files = Get-ChildItem ...`, а затем используй `$files.Count` и `$files | ForEach-Object`.
- Ограничивай глубину рекурсии: используй параметр `-Depth 2` или `-Depth 3`, если не уверен в размере папки. Избегай бездумного `-Recurse` на корневых дисках или огромных папках (например, `C:\Users`).

### PowerShell Execution: Blacklist & Whitelist (Исполнение PowerShell)

Эти правила обязательны при генерации ЛЮБЫХ команд для терминала.

#### 🔴 ЧЁРНЫЙ СПИСОК (КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО)
Эти команды буферизируют вывод, требуют интерактивного ввода или вызывают бесконечное ожидание. Их использование = мгновенный FAIL.

1. Интерактивные команды (требуют ввода пользователя):
   - `Out-GridView`, `Show-Command`, `Show-ControlPanelItem`, `Show-EventLog`, `Read-Host`
   - Любые команды с параметром `-Paging` (например, `Out-Host -Paging`)
2. Форматирование вывода (буферизирует всё в память перед печатью):
   - `Format-Table` (особенно с `-AutoSize` или `-Wrap`), `Format-List`, `Format-Wide`, `Format-Hex`
   - Вместо них: `Select-Object` или `ForEach-Object { "$($_.Prop) - $($_.Other)" }`
3. Опасные конструкции запуска:
   - `Start-Process ... -Wait` с `-RedirectStandardOutput` или `-RedirectStandardError` (дескрипторы не закрываются, процесс висит)
   - `Invoke-Expression` (`iex`)
   - Бесконечные циклы (`while($true)`) без явного условия выхода или таймаута
   - `Start-Sleep` для ожидания завершения другого процесса (используй `Wait-Process`)
4. Неэффективные или рискованные вызовы:
   - Двойной вызов тяжёлых команд (например, `Get-ChildItem -Recurse` дважды). ВСЕГДА сохраняй результат в переменную: `$files = Get-ChildItem ...; $files.Count`
   - `Get-ChildItem -Recurse` без `-Depth` на больших папках (`C:\`, `C:\Users`, `C:\Windows`)
   - `$ErrorActionPreference = 'Continue'` (по умолчанию) — используй `'Stop'`

#### 🟢 БЕЛЫЙ СПИСОК (ОБЯЗАТЕЛЬНО ИСПОЛЬЗОВАТЬ)
1. Прелюдия к любому сложному скрипту:
   ```powershell
   $ErrorActionPreference = 'Stop'
   $ProgressPreference = 'SilentlyContinue'
   ```
2. Вывод данных:
   - `Select-Object` для выбора свойств
   - `ForEach-Object { "$($_.Name) - $($_.Length) bytes" }` для построчного вывода
   - `Write-Output` или `Write-Host` для статусных сообщений (умеренно)
3. Работа с файлами:
   - `Test-Path` перед доступом к файлу/папке
   - `-ErrorAction SilentlyContinue` для некритичных ошибок (например, при поиске)
   - `-Depth 2` или `-Depth 3` для `Get-ChildItem -Recurse`
4. Запуск внешних процессов:
   - Прямой вызов: `& "C:\path\to\script.ps1"` или `powershell.exe -File "C:\path\to\script.ps1"`
   - Для повышения прав: `Start-Process powershell -Verb RunAs -ArgumentList '-File "C:\path\to\script.ps1"'` (БЕЗ `-Wait` и БЕЗ перенаправления вывода)
5. Ожидание:
   - `Wait-Process -Name "processname"` (с параметром `-Timeout`)
   - `Start-Sleep` только для коротких пауз (не для ожидания завершения)

#### Безопасный запуск скриптов (Safe script launch)
- КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО использовать `Start-Process ... -Wait` вместе с `-RedirectStandardOutput`/`-RedirectStandardError` для запуска PowerShell-скриптов — эта конструкция приводит к вечному зависанию (дескрипторы перенаправления не закрываются, процесс висит).
- Если нужно запустить скрипт и дождаться завершения — используй прямой вызов: `& "C:\path\to\script.ps1"` или `powershell.exe -File "C:\path\to\script.ps1"`. Это корректно дожидается завершения и возвращает вывод в терминал.
- Если скрипту нужны права Администратора — запускай через `Start-Process powershell -Verb RunAs -ArgumentList '-File "C:\path\to\script.ps1"'`, но БЕЗ `-Wait` и БЕЗ перенаправления вывода. После запуска сообщи пользователю, что скрипт работает в отдельном окне, и попроси проверить результат вручную.
- Для длительных операций (сборка, установка) используй фоновые задания (`Start-Job`) или запускай скрипт в отдельном окне и проверяй статус позже — не блокируй терминал через `-Wait`.

### PowerShell 7 Safety Rules (Защита от зависаний PowerShell 7)
- ВСЕГДА добавляй `$ErrorActionPreference = 'Stop'` в начало сложных скриптов. Это заставит PowerShell остановиться на первой ошибке, а не генерировать тысячи строк ошибок, которые «топят» Cline.
- ИЗБЕГАЙ интерактивных команд и конструкций, которые могут «повиснуть» (например, `Read-Host`, `Out-GridView`).
- Для команд, которые выводят много текста (например, логи, списки файлов), ИСПОЛЬЗУЙ перенаправление в файл и затем читай его через инструмент чтения файлов (`read_files`), а не полагайся на прямой вывод в терминал. Это обходит сломанную shell-интеграцию Cline.
- Всегда добавляй `; Write-Host "EXIT:$LASTEXITCODE"` в конец команды. Это послужит чётким маркером завершения для Cline.
