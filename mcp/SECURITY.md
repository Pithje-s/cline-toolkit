# Аудит MCP-серверов перед подключением

MCP-сервер — это код, который агент вызывает с реальными правами (файловая
система, сеть, шелл). Подключение сервера — решение по безопасности, а не
удобство. Проходите чек-лист **до** того, как добавить сервер в
`cline_mcp_settings.json` и включить его.

## Чек-лист

- [ ] **Источник.** Сервер из официального репозитория/издателя? Ссылка на исходники есть?
- [ ] **Известность.** Проект имеет историю, звёзды, релизы, поддерживается? Не безымянный форк?
- [ ] **Права доступа.** Какие tool'ы предоставляет? Нужен ли ему доступ к ФС/сети/шелу?
      Выдаются ли только минимально необходимые права?
- [ ] **Чувствительные пути.** Сервер не получает доступ к `.ssh`, `.aws`, `.env`,
      системным каталогам без явной необходимости?
- [ ] **Секреты.** Как сервер принимает ключи/токены? Передаются ли они в URL/аргументах
      (видно в конфиге и логах) или через переменные окружения?
- [ ] **Версия.** Версия закреплена (pinned), а не «latest»?
- [ ] **Сеть.** Сервер не отправляет данные наружу без явной на то причины?
- [ ] **Allowlist.** Сервер добавлен в `mcp.allowlist` в `config.example.json` осознанно,
      а не «на всякий случай»?
- [ ] **Подтверждение.** Явное подтверждение пользователя на добавление получено
      (см. правило `rules/02-quality-git.md` → «Безопасность MCP-серверов»).

## Красные флаги (STOP)

- Неизвестный издатель + широкие права (полный доступ к ФС/шелу).
- Ключи передаются прямо в URL/аргументах командной строки.
- Обещанная функциональность не соответствует запрашиваемым правам.
- Нет исходников/невозможно проверить, что делает сервер.

При любом красном флаге — **не подключать**, сообщить пользователю и запросить
подтверждение либо альтернативу.

## После подключения

- Держите реальные ключи вне репозитория (плейсхолдеры в шаблоне).
- Периодически пересматривайте список серверов: отключайте неиспользуемые.
- При обновлении сервера — перепроверьте пункт «Права доступа».
