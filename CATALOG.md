## rules/ — правила

Глобальные правила загружаются в каждый диалог и задают базовую дисциплину.
Три файла читаются последовательно (01 → 02 → 03).

| Файл | О чём | Ключевые темы |
|---|---|---|
| `01-core.md` | Базовые правила поведения | Данные vs Команды (правило верхнего уровня), запрет галлюцинаций, обязательный план, одна задача за раз, дисциплина выполнения, Zero Placeholders, точечное чтение, безопасность команд, «действие важнее советов», оркестрация следующего шага |
| `02-quality-git.md` | Качество кода и git | Секреты и `eval`/`exec`, аудит MCP-серверов, качество кода, комментарии (why, не what), Conventional Commits и git-дисциплина, язык ответа |
| `03-workflow-search.md` | Рабочие процессы и поиск | Правило 3 попыток (эскалация в `external-research`), внешний поиск через MCP/OpenRouter, запрет выдуманных API |

> Платформенные детали (чёрный/белый список PowerShell, UAC, защита от зависаний,
> ловушки stderr/BOM) вынесены в навык `powershell-safety`: они нужны не в каждом
> диалоге, а по требованию. В `01-core.md` остались инвариант и ссылка — так
> постоянная стоимость контекста меньше.

## skills/ — навыки

Каждый навык — папка с `SKILL.md` (метаданные `name`/`description` + инструкции).
Навыки комбинируются: например, `error-stack-analyzer` передаёт найденное место
в `repair-loop`, а тот после 3 неудач — в `external-research`.

| Навык | Что делает | Когда вызывать |
|---|---|---|
| `design-twice` | Предлагает ДВА существенно разных архитектурных подхода (A/B), сравнивает по критериям и ждёт выбора | Перед крупной фичей или рефакторингом («спланируй», «как лучше сделать») |
| `independent-review` | Независимое ревью диффа «глазами другого инженера»: вердикт с находками по severity, без переписывания | Ревью перед коммитом/мержем («ревью», «проверь дифф») |
| `error-stack-analyzer` | Разбирает большой стектрейс, находит первую строку в НАШЕМ коде и объясняет root cause | Падения, исключения, трейсбеки («разбери ошибку») |
| `repair-loop` | Цикл «исправить → перепроверить → повторить» до зелёного результата | Падают тесты/сборка/линт/типы («почини», «исправь») |
| `external-research` | Эскалация при исчерпании локальных знаний: точные запросы или готовые ссылки, без выдуманных API | После 3 неудач `repair-loop` или незнакомая ошибка/API |
| `safe-dependency` | Проверка пакета перед установкой: анти-typosquatting, стабильная версия, предупреждение о тяжёлых пакетах | Установка/добавление/обновление зависимости |
| `verify-changes` | Доказывает, что правка реально применена и работает (diff + запуск + отчёт с доказательствами) | Перед завершением любой задачи, менявшей файлы |
| `system-optimizer` | Оптимизация ОС/игр/софта кодом (PowerShell/реестр/конфиги) с обязательным бэкапом, а не советами | «Ускори», «убери лаги», «настрой под слабый ПК», правка реестра |
| `powershell-safety` | Правила терминала: чёрный/белый список команд, запуск скриптов и ожидание процессов, UAC-самоподъём, защита от зависаний и ловушки (stderr + `ErrorActionPreference=Stop`, BOM, массивы, `$null`) | Генерация PowerShell-команд и `.ps1`, зависший терминал, «нужны права администратора» |
| `next-step-orchestrator` | После завершения задачи генерирует следующий управляющий промпт (цикл план→реализация→верификация→ревью→память) | Задача завершена, получен отчёт или возникла развилка |

## workflows/ — воркфлоу

Сценарии-обёртки (`.md`), активируются командой (`/plan`, `/review`, `/fix` и т.п.)
или текстом. Многие просто включают одноимённый навык; подкатегория `memory-bank-*`
служит для хранения состояния проекта между сессиями.

### Рабочие сценарии

| Воркфлоу | Зачем | Триггер |
|---|---|---|
| `plan.md` | Включает `design-twice` — два архитектурных подхода перед реализацией | `/plan`, планирование задачи |
| `review.md` | Включает `independent-review` — senior-вердикт по текущему диффу | `/review` |
| `verify.md` | Включает `verify-changes` — доказательство завершённости задачи | `/verify` |
| `fix.md` | Включает `repair-loop` — починка с лимитом 3 попытки | `/fix` |
| `repair.md` | Цикл исправление→проверка→повтор до зелёного | Красная проверка (тесты/сборка/линт) |
| `error-stack-analyzer.md` | Разбор стектрейса и root cause | `/error-stack-analyzer`, анализ падения |
| `external-research.md` | Исследование при исчерпании локальных знаний | После 3 фейлов `repair-loop` |
| `safe-dependency.md` | Безопасная установка зависимостей (анти-typosquatting) | Установка пакета |
| `system-optimizer.md` | Оптимизация ОС/игр/софта кодом с бэкапом | Запрос на ускорение/настройку |
| `next-step-orchestrator.md` | Генерация следующего шага цикла разработки | Задача завершена |
| `precommit-check.md` | Финальный чек-лист «проверено, прежде чем declaring done» | Перед завершением задачи |

### memory-bank-* (состояние проекта)

Система «банка памяти»: файлы-шаблоны, в которых агент ведёт состояние проекта,
чтобы не терять контекст между сессиями.

| Воркфлоу | Файл памяти | Содержание |
|---|---|---|
| `memory-bank.md` | (ядро) | Оркестрация чтения/записи всего Memory Bank |
| `memory-bank-product.md` | `product.md` | Что строим и зачем |
| `memory-bank-productContext.md` | `productContext.md` | Контекст продукта |
| `memory-bank-tech.md` | `techContext.md` | Стек и технологии |
| `memory-bank-structure.md` | `systemPatterns.md` | Архитектура и паттерны |
| `memory-bank-context.md` | `activeContext.md` | Текущий фокус и состояние |
| `memory-bank-progress.md` | `progress.md` | Статус и прогресс |
| `memory-bank-decisions.md` | `decisionsLog.md` | Журнал решений |
| `memory-bank-nextTask.md` | `nextTask.md` | Следующая задача |
| `memory-consolidation.md` | — | Сжатие/чистка Memory Bank при переполнении контекста (вручную) |

## mcp/ — MCP-серверы

Конфигурация внешних инструментов через Model Context Protocol. В репозитории —
очищенный шаблон: рабочий `tavily` с плейсхолдером ключа и выключенные заготовки.

| Сервер | Тип | Назначение | Статус в шаблоне |
|---|---|---|---|
| `tavily` | streamableHttp | Веб-поиск и AI-research | включён, ключ = `YOUR_TAVILY_API_KEY` |
| `fetch` | stdio (`uvx`) | Загрузка и парсинг веб-страниц | `disabled: true` |
| `filesystem` | stdio (`npx`) | Ограниченный доступ к файловой системе | `disabled: true` |
| `git` | stdio (`uvx`) | Операции с локальным git-репозиторием | `disabled: true` |
| `memory` | stdio (`npx`) | Долговременная память между сессиями | `disabled: true` |

Заготовки включаются установкой `"disabled": false` и указанием реальных путей
(для `filesystem` и `git`). Ключ Tavily храните вне репозитория — см. раздел
«Безопасность» в [README](README.md).

Перед подключением любого сервера — пройдите чек-лист аудита:
[`mcp/SECURITY.md`](mcp/SECURITY.md) (источник, права, секреты, allowlist).

## Инженерная обвязка

- `validate.ps1` — проверка целостности: frontmatter, JSON, секреты, CJK, дубли и потенциальные противоречия, наличие файлов поставки, регресс-гард на устаревшие директивы.
- `.github/workflows/validate.yml` — CI: валидатор + Pester-тесты на push/PR.
- `config.example.json` — advisory-параметры (язык, лимит попыток, пороги плана, allowlist).
- `install.ps1` — установка в глобальные каталоги Cline: неразрушающий merge MCP-конфига (существующие серверы и ключи сохраняются, недостающие добавляются), бэкап `cline_mcp_settings.json.bak-<timestamp>`, манифест установки и prune устаревших файлов прошлой версии по хешу.
- `uninstall.ps1` — удаление строго по манифесту: `-DryRun`, `-Force`, `-RestoreMcpBackup`.
- `tests/` — Pester-тесты установщика (merge MCP, манифест, prune, uninstall), тесты метрик и валидности eval-задач, раннер `run-tests.ps1`.
- `eval/` — харнесс измерений: задачи-фикстуры, метрики по диффу и логу, измеритель стоимости контекста (см. [EVAL.md](EVAL.md)).
- `CHANGELOG.md` / `CONTRIBUTING.md` / `LICENSE` — версионирование, правила вклада, лицензия (MIT).
